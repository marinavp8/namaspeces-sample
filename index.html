Un contenedor en 300 líneas de Go

Alpine Linux, unshare, una capa overlay y pivot_root, sin Docker ni runc. Primero como script de shell y después como programa en Go, probado en un VPS Ubuntu.

Go · solo librería estándar Alpine minirootfs 3.22.0 cgroup v2 probado en x86_64

Qué se ha hecho

El objetivo era lanzar el equivalente a un contenedor usando una imagen de Alpine ARM, unshare y un sistema de ficheros overlay. Un contenedor es un proceso de Linux con namespaces que le aíslan la vista del sistema, un sistema de ficheros raíz propio y, opcionalmente, límites de recursos.

  1. Se explicó el método y se escribió mini-run.sh, una versión en shell.
  2. Se reescribió en Go como mini, que sale como un binario estático sin dependencias.
  3. Se compiló para linux/amd64 y linux/arm64 y se probó por SSH en un VPS (x86_64, Ubuntu, kernel 7.0).
  4. Las pruebas encontraron dos fallos y los dos están corregidos.

Cómo funciona

El sistema de ficheros del contenedor es un overlay de dos capas. La base de Alpine se queda como solo lectura y todo lo que escribe el contenedor va a su propia capa.

merged/lo que ve el contenedor como /
c/<nombre>/upperescrituras de este contenedor
lower/Alpine minirootfs, compartido y de solo lectura

Varios contenedores comparten el mismo lower y cada uno tiene su upper y su work. Para resetear uno basta con borrar su upper.

Secuencia de mini run

El binario se lanza dos veces: primero como proceso del host y después como child, ya dentro de los namespaces.

host Prepara

Crea upper, work y merged. Abre un pipe de sincronización.

host Clona

Se relanza con /proc/self/exe child y las flags CLONE_NEW*.

host Configura

Mete el PID en un cgroup con memory.max y crea el par veth con NAT si se pidió --net.

host Libera

Escribe un byte en el pipe y espera a que el hijo termine. Después borra veth y cgroup.

child Espera

Lee el pipe (fd 3) hasta que el host termina cgroup y red. Después configura eth0.

child Monta

Hace el montaje privado, monta el overlay, /proc, /sys, bind de /dev, escribe resolv.conf y fija el hostname.

child Entra

pivot_root, desmonta el host con MNT_DETACH y hace exec del programa, que queda como PID 1.

Uso

sudo ./mini init                          # descarga el minirootfs a /var/lib/mini/lower
sudo ./mini run web                       # shell en el contenedor "web"
sudo ./mini run --net --mem 256M web      # con red aislada y límite de RAM
sudo ./mini run db -- apk add redis       # ejecuta un comando concreto
sudo ./mini reset web                     # borra la capa de escritura
sudo ./mini ls

Para compilar: GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o mini-linux-arm64 .

Resultado de las pruebas

Ejecutadas por SSH en un VPS: x86_64, Ubuntu, kernel 7.0.0-42, cgroup v2 y overlay disponibles.

  • Descarga y extracción del minirootfsOK
  • Aislamiento: PID 1, hostname propio, ps limitadoOK
  • Overlay: lo escrito va a upper y lower queda intactoOK
  • Red: eth0 con IP propia y ping a 1.1.1.1OK
  • DNS, apk add curl y curl https://example.comOKFunciona tras el segundo arreglo.
  • Dos contenedores con red a la vezOK
  • Limpieza al salir de veths, mounts y cgroupsOK
  • Límite de memoriaPARCIALmemory.max queda fijado en 32 MB y se alcanzó 323 veces, pero no hubo oom_kill: el host tiene swap y el kernel movió las páginas ahí.

Fallos encontrados y corregidos

El veth no se encontraba dentro del netns. /sys se montaba antes de entrar al netns y /sys/class/net mostraba las interfaces del host. Ahora se busca con ip -o link, que consulta el kernel directamente.

Sin DNS en el contenedor. El resolv.conf del host apunta al stub 127.0.0.53 de systemd-resolved, que no existe en otro netns. Ahora se usa /run/systemd/resolve/resolv.conf y, si no hay, 1.1.1.1 y 8.8.8.8.

Limitaciones y siguientes pasos

  • Límite de memoria blando con swap. Para hacerlo estricto hay que escribir también memory.swap.max=0. Es una línea en setupCgroup.
  • Zombies. El programa lanzado es PID 1 y no recoge procesos huérfanos. Para algo serio habría que añadir un mini-init o usar tini.
  • Subred por hash. Dos nombres de contenedor pueden dar la misma subred, con una probabilidad baja.
  • ARM sin probar. El binario arm64 compila, pero las pruebas reales fueron solo en x86_64.
  • Sin ISO. Se usa el minirootfs en lugar de la ISO de Alpine, porque la ISO contiene kernel y paquetes, no un rootfs. Si se quiere partir de la ISO, se puede añadir un init-iso que instale alpine-base con apk --root.
  • Solo root. No hay modo rootless con user namespace.

Estado en el servidor de pruebas. Los contenedores de prueba están borrados. Quedan el binario en /tmp/mini y el rootfs en /var/lib/mini/lower.
